# 等待窗口工作：把工具等待用于准备材料

## 目标与定位

在普通 Agent 循环中，一个或多个工具调用等待返回时，允许模型完成一项只依赖现有文本材料的准备工作。目标不是让推理始终忙碌，也不是预测尚未返回的工具结果；没有可用工作时继续等待。

这是默认关闭的实验能力。已有静态 DAG 路径保持独立。本轮不引入其他模型供应商，不实现写操作推测、事务回滚或通用自动依赖证明。

## 机制

### 提案搭便车

主模型在正常生成工具调用的同一响应里，可以附带一个 `ooo-work` 标签，内容为严格 JSON 的 `task` 字符串。提案属于公开可检查的任务说明，不是模型私有 reasoning。只读取当前 assistant 的文本块；历史输入、工具参数、工具结果中的同名标签不是执行指令。没有提案时，不额外调用模型寻找工作。

提案不是事实独立性的证明。程序只能限制可用输入和执行能力，主模型仍需检查返回的准备材料。第一版适合整理已有证据、列出待核验问题、审查已提供文本，不适合必须知道未完成工具结果才能得出结论的任务。

### 实际等待授予执行机会

只有真实进入 dispatch 且被宿主分类为可并发的工具才提供等待机会。prepare、权限等待、结果 finalize 和 exclusive 工具不计入。等待超过可配置宽限时间后才启动辅助调用，避免快速工具产生无意义额外开销。

每个 step 只使用首个合格的连续活动区间；在飞数量第一次归零就关闭，不在后续滚动补位或工具组中重新启动。每 turn 另有限定调用预算，实际启动即计入，失败不退款。

### 输入冻结、执行受限、产物待验

准备工作使用当前主请求发出前的文本快照，不把当前未配对的工具调用历史直接交给提供方，不伪造占位工具结果，不复制私有 reasoning。无法完整容纳或包含不支持的模态时跳过，而不是静默删减材料。

辅助请求继承本步已准入的路由配置，另行准备调用并经过 LLM stream 中间件。它不重跑可能有状态的 `agent/request` 路由链，不冒充主会话请求、不改写主 request header。辅助请求使用独立标识，避免消耗主请求的回放游标。

辅助模型没有工具可用。只有完整正常结束、非空且在长度限制内的文本才成为候选材料。工具调用、截断、错误、超时和关闭后的迟到结果均不能被采用。取消、新输入、工具错误或主任务已经结束，也会使材料失效。

### 前台优先与后台槽位

工具等待结束时同步关闭结果接纳并请求取消，主任务不为辅助调用无界等待。未退出的辅助调用继续占据该会话的槽位，直到真实退出；因此关闭并不意味着可无限启动替代请求。

这不能强制终止不合作的 middleware/provider，也不能保证取消的调用不计费。取消传播期间，主请求与尚未退出的辅助请求可能暂时同时存在。该限制必须纳入资源和成本评估。

### 使用现有会话协议交付

候选材料通过来源明确的 plugin user message 进入下一正常 step，由主模型结合真正的工具结果核验。它不是工具结果、不是最终答案，也不拥有执行授权。工具调用和结果原有的顺序与配对不变；已结束的 turn 不应为了报告辅助状态而再开一轮。

不新增宿主不认识的 SessionEventMap 类型。成功进入主任务的材料沿现有日志路径保存；辅助请求状态与用量通过独立的实时观察通道报告。实时统计不等于持久计费账本或执行恢复，缺失 usage 必须保持未知，不能记成零。

## 配置与复现

在固定版本 Harness 中用本包替换 `dsh-agent-loop`，不要同时加载两个 loop provider。普通循环省略 `waitWork` 即关闭；不要为这个功能配置 `dag`。

```yaml
- name: '@deepseek-ai/dsh-ooo-loop'
  config:
    waitWork:
      graceMs: 100
      maxRunMs: 3000
      maxTokens: 256
      maxCallsPerTurn: 1
      maxSnapshotChars: 16000
      maxResultChars: 4000
    agents: []
```

若部署使用 `complete: true` 的完整系统提示词，宿主会保留其精确文本，不自动添加本插件的提案协议。此时需在自己的完整提示词中说明 `<ooo-work>{"task":"只依赖已有文本的准备任务"}</ooo-work>` 协议；仅启用配置不保证模型知道如何提案。

这些值是显式配置示例，不是收益最优值。`maxTokens` 限制辅助输出，`maxSnapshotChars` 限制输入字符数，两者不能等同输入加输出的总 token 硬上限。保留宿主现有 agent、模型路由和工具注册配置。

按 [插件集成步骤](../dsh-plugin/README.md) 安装后，从宿主根目录执行：

```sh
OOO_WAIT_BENCHMARK_OUTPUT=/tmp/wait-work-comparison.json \
  pnpm exec vitest run --config packages/experimental/ooo-loop/vitest.config.ts \
  packages/experimental/ooo-loop/tests/wait-work-loader.spec.ts
```

该测试使用真实 Loader、YAML 配置和普通 loop；仅模型与外部读取为确定性模拟。两组运行同一准备任务，断言工具等待与准备工作的事件重叠、最终结果一致、辅助材料持久化及插件卸载清理。不设置输出变量时不生成对照 JSON。毫秒记录包含运行时预热差异，不能据此推算真实模型加速比例。

## 评测原则

分别评估调度行为和真实任务收益。确定性 mock 只能验证实际重叠、正确取消、无额外主循环阻塞和产物传递，不能当成真实模型速度提升。

端到端对照需要相同任务、材料、完成要求和工具权限；同时记录提案、辅助推理、结果汇总的调用数、token 和费用。对照必须包含只有一个慢工具的任务，以及没有独立工作、工具很快、准备工作来不及完成的负例。

验收重点是最终任务完成质量与总耗时，而不是推理忙碌占比。准备材料没有被使用、因失效被丢弃或拖慢结果处理，都应公开计入成本。

## 明确保留的边界

- 默认关闭；现阶段只有被分类为可并发的工具等待才合格。
- 一项文本准备任务，不是完整动态规划器；不对语义独立性作形式保证。
- 不读取尚未返回的结果；不允许辅助工具执行或外部写入。
- 不提供在飞辅助调用的跨进程恢复，不保证提供方合作取消。
- 不声称降低费用或提高真实任务质量，需由真实任务对照验证。
